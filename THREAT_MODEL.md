# Threat model (summary)

Trust boundaries:
- **Home hub (main path):** phones (over adb reverse) and local MCP clients → hub on 127.0.0.1 → simulated devices; the hub calls the Ring API (Playground token in memory), Amazon SNS / CloudWatch / Bedrock (AWS CLI profile) and the family relay.
- **Family relay:** hub (Ed25519) ⇄ public Lambda function URL + DynamoDB ⇄ enabled phone (WebCrypto P-256). The relay is untrusted for decisions: the hub verifies every phone signature itself. Ring ⇒ the relay's public `POST /ring/webhook` (X-Signature HMAC) ⇒ the hub pulls the queued events over its Ed25519-signed channel.

| Threat | Mitigation |
|---|---|
| A stranger pairing a phone | One-time 8-digit code (10 min, single use, 5 failures/min → 1 min lock) **and** the owner pressing **Allow** in a macOS system dialog on the hub (typing `y` in the hub terminal is the fallback; the phone can reach neither), with matching check digits; family phones need **Allow** on the admin phone; members cannot be approved before an admin exists; Origin check on the unauthenticated phone routes |
| A copied phone credential | Only SHA-256 digests stored (0600 file in a 0700 folder); the credential is only traded for a 1-hour session and rotated on every trade; reuse of any recently rotated-out credential revokes that phone and its sessions at once (no grace window; the phone page serialises its own uses, so a double tap on the phone does not trip it, but two raw clients sharing one credential do); owner revoke is immediate; no inactivity expiry by owner choice (trusted until removed) |
| A family phone doing admin things | Members get state and everyday actions only; door unlock and camera disarm refused on `/api/action` and `/mcp`; pairing, phone list, Ring, Wi-Fi, cloud and device pairing routes return `MEMBER_NOT_ALLOWED`; the last admin cannot be revoked |
| A silent outage (camera, gateway or hub) | Low-frequency heartbeats with explicit late/offline states; alerts on every state change; a CloudWatch alarm with missing data treated as breaching emails the family when the hub itself goes quiet |
| A scheduled action that never happened | Each routine run ends as confirmed (receipt), not executed or unknown; missed runs are never replayed automatically (a family member decides); unlock/disarm can never be routine items |
| Email alert credentials | The hub shells out to the AWS CLI with a dedicated profile; the IAM user may only publish to one topic and write one metric namespace; alert text carries no personal data, tokens or images; 10 emails per hour, failures print `ERROR sns ...` |
| An AI agent (or anyone holding a session) opens the door | Unlock is only ever a request; deciding needs the admin phone's long-lived credential (rotated on use, reuse revokes the phone) and a session from that same phone, or a signed answer from a phone the admin enabled for remote approval (see below); the one-use confirmation is minted and spent server side and never handed to a client; single use, 60 s, one at a time; cloud, schedules and batches still refuse unlock |
| A forged or replayed remote approval | The hub signs every relay call with an Ed25519 key whose public key is pinned in the stack; each enabled phone signs with its own non-extractable WebCrypto P-256 key; the hub verifies the phone's signature with the public key **it** stored at activation, so a decision written by the cloud or by another phone is rejected; nonces, 10-minute one-time enrolment codes, first-write-wins per request, TTL on every row; a 4xx is never retried |
| A compromised or misbehaving relay | It can withhold or delay messages (the door then stays locked; the admin phone at home still decides) but cannot create an approval; it only ever sees text (who asks, seconds left), never snapshots, face hints or tokens; its role can only read and write its own table |
| A fake or wrong board posing as the home gateway (ESP32-C3 on USB) | The hub opens only USB serial ports whose USB device is made by Espressif (vendor id 0x303a, read from macOS `ioreg`) or the one port named in `HOME_MCP_USB_GATEWAY_PORT`; a board must first say hello as `hmg-home-gateway`, any other is asked once and closed; only three small JSON line types are accepted (hello, beat, button), anything else is ignored; the gateway cannot open the door or run devices, it only reports heartbeats and button presses |
| An AI agent doing more than it should with ordinary devices | Tiered permissions (`src/agent_policy.mjs`): an MCP client may run only low-risk actions inside the family's limits (lights; AC 24–28 °C; dehumidifier 40–60 %; vacuum 08:00–20:00; alarm 05:00–10:00; arm; lock); anything else is refused before the simulator and shown on the timeline; door unlock stays a request a trusted phone approves |
| A forged, replayed or flooded Ring webhook | The relay accepts an event only with a valid `X-Signature` (`sha256=` + HMAC-SHA256 of the raw body, compared in constant time; no key configured = 503); a repeated `meta.request_id` is dropped; only five event types are queued and only type, sub-type, device id and time are kept, for 24 h; bodies over 16 KB are refused; the hub reads at most 20 events per signed pull, its first pull only records the position, and a doorbell or person event older than 2 minutes never becomes a door request. Even a valid event only creates a request: the door still needs a trusted phone |
| Ring Chime used to disturb the person at home | Plays only with `HOME_MCP_CHIME=on` and a Ring token loaded, at the same moments as the voice notice, at most once a minute; skipped when the Chime is offline or snoozed; only a slot the owner configured (`audio_ref`) is played, never caller-supplied audio |
| A care note that invents facts | Bedrock gets only the day's facts (times, devices, outcomes); every number in the note must appear in those facts or the family gets the template note instead; the model has no tools and cannot act |
| Ring token exposure through live view | The phone sends only its WebRTC offer; the hub adds the token and keeps Ring's session URL; one stream at a time, at most 60 s, closed when the request ends |
| Face data misuse | Hint only (never part of the decision); enrolment by the admin phone only with an explicit consent flag; only the SFace feature is kept, AES-256-GCM with the key in a separate 0600 file; delete one / delete all (file and key removed); hint shown on the admin banner only, never in MCP answers, requester status, email or logs; image decoding runs in a separate local Python process |
| Door snapshot leaks | Memory only, dropped when the request ends; admin phone only (`no-store`, own CSP); never in email, logs or files; Ring token never sent to the pre-signed image URL |
| Local attacker in the browser | Loopback-only server, Host/Origin checks, separate operator code with rate limit for every Ring action, no secrets sent to the page |

Known residual risks (current): a paired phone's credential sits in that browser's localStorage, so script running in the console page on that phone could use it (rotation turns a later copy into a revoke, not a prevention); a trusted phone never expires on its own (owner choice), so removal is the control and a lost phone must be removed; an admin phone stands in for the operator code; phones reach the loopback server through adb reverse in this version, and plain-HTTP LAN access is not supported because it would expose the credential on Wi-Fi; the relay URL is public by design (unauthenticated callers get refusals; abuse could cost DynamoDB/Lambda requests, not a door opening); an enabled phone's signing key lives in that browser's IndexedDB (non-extractable, but usable by script on that page) until the admin removes the phone; the Ring webhook HMAC key is a NoEcho stack parameter but sits in the relay Lambda's environment, so anyone in the AWS account allowed to read the function configuration can read it; the relay is trusted for webhook events, so a compromised relay could insert or replay events (at worst a door request that a phone must still approve, or a wrong camera state until the next event or status check); `device_online` / `device_offline` events carry no age limit, so a delayed one can set the camera state late; an AI agent's door request makes the Chime sound like any other door request (once a minute at most). Anyone with physical access to the Mac could plug in an ESP32 flashed with the same firmware id and send heartbeats or button presses: it can raise or calm gateway alerts and send a help email, but cannot open the door or run a device.

## Earlier phase: cloud MCP chain

Kept for reference; not part of the current demo. See [docs/EARLIER_PHASE_CLOUD_MCP.md](docs/EARLIER_PHASE_CLOUD_MCP.md).

Trust boundary: MCP client → API Gateway → Lambda (MCP server) → DynamoDB/KMS → owner's Mac worker → local console (simulated devices).

| Threat | Mitigation |
|---|---|
| Someone other than the owner issues commands | Cognito MFA + PKCE, single admin-created owner, Ring account pinned to the owner (SHA-256, constant-time compare), MCP resource-server scopes |
| Reuse of an approval or Ring token | Single-use bootstrap/renewal latches, 1-hour Ring token replay marker, failure budget (3 definite rejections → 1 h lock) |
| Replay or duplication of a command | Idempotent command ids, single-slot mailbox, 30-second TTL, claim-token hash, Mac journal (apply at most once), proof nonces |
| A fake or impersonated Mac | Operator-approved Ed25519 key enrollment; every fetch/receipt carries a signed proof over owner, operation, audience, token hash, payload hash and nonce (≤ 15 s) |
| "Accepted" reported as "executed" | `executed=true` only after a receipt matching the claim, envelope hash, Mac key and exact device/action |
| Cloud compromise opening the door | Door unlock, camera disarm and value actions are not in the cloud allowlist; the Mac worker and the local console enforce the same allowlist; local unlock needs a one-use confirmation |
| A refused command running later | Cloud-origin commands are never queued locally (applied immediately or refused) |
| Silent infrastructure change | Gateway admission file pins API id, stage, domain and function, and rejects a request whose deployment id differs from the pinned one; a redeploy requires re-admission |
| Local attacker using an active cloud login | The operator code is also asked once per cloud login; cloud actions then reuse that login until its ~5-minute token expires |

Known residual risks (earlier phase): while a cloud login is active, script running in the console page could send allowlisted cloud actions without re-entering the operator code (never unlock, disarm or value settings); reduced-assurance Mac mode (no local anti-rollback/Wi-Fi trust re-check), operator-built approval files, sandbox-only Ring identity.
